# AI & LLM Inference Cheat Sheet

A quick reference for AI inference, LLM serving, GPU management, distributed inference, Kubernetes, routing, and observability.

> **Note:** Some abbreviations vary by project or dashboard. Check the metric definition before comparing measurements.

## 1. Inference performance and latency

| Short form | Full form | Meaning |
|---|---|---|
| **TTFT** | Time to First Token | Time from request arrival until the first generated token is delivered. |
| **TPOT** | Time Per Output Token | Average time per output token after the first token. |
| **ITL** | Inter-Token Latency | Time between consecutive output tokens. |
| **E2E** | End-to-End Latency | Total time from request start to completion. |
| **TPS** | Tokens Per Second | Token generation rate; clarify whether per request or aggregate. |
| **RPS** | Requests Per Second | Request throughput. |
| **QPS** | Queries Per Second | Query throughput. |
| **P50 / P90 / P95 / P99** | Percentiles | Latency thresholds below which 50%, 90%, 95%, or 99% of observations fall. |
| **SLI** | Service-Level Indicator | A measured service-health signal. |
| **SLO** | Service-Level Objective | A target for an SLI, such as latency or availability. |
| **SLA** | Service-Level Agreement | A formal service commitment. |
| **TTFB** | Time to First Byte | Time until the first response byte arrives; not the same as TTFT. |

### Important distinction
- **TTFT** measures perceived response start.
- **TPOT / ITL** measure how quickly the response continues to stream.
- **E2E latency** measures total completion time.
- **TPS** measures throughput, not necessarily latency.

## 13. Useful formulas

### Approximate TTFT
`TTFT ≈ queueing time + prefill time + serving/network overhead`

The exact measurement boundary depends on the serving stack and client instrumentation.

### Output generation rate
`TPS = output tokens / measured generation time`

Be explicit about whether this is per-request generation speed or aggregate server throughput.

### Approximate TPOT
`TPOT ≈ time between first and last output token / (output token count − 1)`

For one output token, TPOT is not meaningfully computed using this formula.

### Approximate model weight memory
`Weight memory (bytes) ≈ parameter count × bits per parameter / 8`

Example: a 7-billion-parameter model using 16-bit weights needs roughly **14 GB (decimal)** for weights alone. Actual deployment memory also includes KV cache, runtime/workspace allocations, activations, and other overhead.

### Bytes vs bits
`1 byte = 8 bits`  
`1 GB/s = 8 Gbps` before protocol overhead.

## Quick interpretation examples

- **High TTFT, normal TPOT:** investigate queueing, prompt length, prefill throughput, and routing.
- **Normal TTFT, high TPOT:** investigate decode speed, GPU memory bandwidth, batch contention, and model configuration.
- **High GPU utilization, low aggregate TPS:** check memory bandwidth, batch composition, model size, throttling, and whether the GPU is doing useful inference work.
- **High request queue depth:** check serving capacity, admission control, batching, and autoscaling.
- **OOM during long prompts:** investigate context length, KV-cache allocation, concurrency, and available GPU memory.
- **Good average latency, poor P99:** inspect queueing spikes, noisy neighbors, cold starts, retries, and workload variance.
